1. Шаблон (патерн) проектування ПЗ: Стратегія 


1.1 Мета роботи 
Метою роботи є дослідження теоретичних засад об'єктно-орієнтованого проєктування програмного забезпечення на основі класичних шаблонів (патернів) проектування Gang of Four (GoF). Поглиблене вивчення, аналіз, practical реалізація та демонстрація поведінкового патерна проєктування «Стратегія» (Strategy) з використанням сучасних засобів розробки та платформ спільної роботи.


1.2 Теоретичні відомості
Патерн «Стратегія» (Strategy) належить до класу поведінкових шаблонів проєктування. Він уперше був описаний у фундаментальній праці Еріха Ґамми, Річарда Гелма, Ральфа Джонсона та Джона Вліссідеса (Gang of Four — GoF) «Design Patterns: Elements of Reusable Object-Oriented Software». Цей патерн визначає сімейство алгоритмів, інкапсулює кожен з них у вигляді окремого класу і робить їх взаємозамінними. Це дозволяє вибирати та змінювати алгоритм під час виконання (runtime) незалежно від об'єктів-клієнтів, які цей алгоритм використовують.
Основна архітектурна проблема, яку вирішує патерн Стратегія, — це уникнення жорсткого кодування поведінки всередині одного класу за допомогою складних умовних конструкцій (таких як if-else або switch). Використання таких конструкцій призводить до створення так званих «божественних класів» (God Objects), які важко модифікувати та тестувати, а також безпосередньо порушує фундаментальний принцип SOLID — Open/Closed Principle (Принцип відкритості/закритості), який стверджує, що програмні сутності мають бути відкритими для розширення, але закритими для модифікації.
        Структура патерна та його учасники:
Context (Контекст): Зберігає посилання на один з об'єктів конкретних стратегій і взаємодіє з ним виключно через загальний інтерфейс. Контекст надає клієнтам інтерфейс для встановлення або зміни поточної стратегії.
Strategy (Стратегія): Визначає загальний інтерфейс для всіх підтримуваних алгоритмів. Він використовується Контекстом для виклику алгоритму, визначеного Конкретною Стратегією.
ConcreteStrategy (Конкретна стратегія): Безпосередньо реалізує конкретний варіант алгоритму чи поведінки.


        1.3 Порівняльний аналіз переваг та недоліків
Застосування шаблону «Стратегія» має системні переваги для архітектури ПЗ, проте супроводжується певними компромісами, наведеними в таблиці нижче.
Переваги патерна Стратегія
	Недоліки патерна Стратегія
 
	Ізоляція коду алгоритмів та їхніх даних від логіки об'єкта-контексту.
	Клієнтський код повинен знати про відмінності між стратегіями, щоб вибрати потрібну.
	Заміна поведінки «на льоту» в процесі виконання програми за рахунок динамічного зв'язування.
	Суттєве збільшення загальної кількості класів у системі за рахунок винесення кожної логіки в окремий файл.
	Забезпечення принципу OCP (Open/Closed Principle) при додаванні нових алгоритмів.
	У деяких мовах програмування ускладнюється архітектура через створення додаткових інтерфейсів.
	

1.4 Практична реалізація та програмний код
Для демонстрації патерна було спроєктовано систему обробки замовлень в інтернет-магазині із гнучким вибором платіжного шлюзу. Нижче наведено лістинг програми мовою C#, де реалізовано інтерфейс стратегії, конкретні класи оплати (Credit Card, PayPal) та клас контексту (ShoppingCart):
using System;
namespace StrategyPatternExample
{
    // 1. Абстракція стратегії
    public interface IPaymentStrategy
    {
        void Pay(int amount);
    }


    // 2. Конкретна стратегія А: Оплата карткою
    public class CreditCardPayment : IPaymentStrategy
    {
        private string _cardNumber;
        
        public CreditCardPayment(string cardNumber)
        {
            _cardNumber = cardNumber;
        }


        public void Pay(int amount)
        {
            Console.WriteLine($"Успішно сплачено {amount} грн за допомогою Credit Card [{_cardNumber}].");
        }
    }


    // 3. Конкретна стратегія Б: Оплата через PayPal
    public class PayPalPayment : IPaymentStrategy
    {
        private string _email;


        public PayPalPayment(string email)
        {
            _email = email;
        }


        public void Pay(int amount)
        {
            Console.WriteLine($"Успішно сплачено {amount} грн через гаманець PayPal [{_email}].");
        }
    }


    // 4. Контекст (Context)
    public class ShoppingCart
    {
        private IPaymentStrategy _paymentStrategy;
        private int _totalAmount = 0;


        public void AddItemPrice(int price)
        {
            _totalAmount += price;
        }


        // Динамічне встановлення стратегії
        public void SetPaymentStrategy(IPaymentStrategy paymentStrategy)
        {
            _paymentStrategy = paymentStrategy;
        }


        public void Checkout()
        {
            if (_paymentStrategy == null)
            {
                Console.WriteLine("Помилка: Спосіб оплати не обрано!");
                return;
            }
            _paymentStrategy.Pay(_totalAmount);
        }
    }
}


1.5 Висновок
Під час виконання практичної роботи №1 було детально вивчено архітектурні аспекти застосування поведінкових шаблонів проєктування GoF. На практичному прикладі мовою C# доведено, що патерн «Стратегія» дозволяє суттєво підвищити гнучкість, масштабованість та підтримуваність коду. Завдяки делегуванню та композиції вдалося повністю ізолювати конкретні реалізації алгоритмів від бізнес-логіки контексту, що спрощує проведення модульного тестування та розширення системи новими методами без зміни існуючої кодової бази.
